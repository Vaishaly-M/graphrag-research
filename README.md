# Adaptive Hybrid GraphRAG Experiment — Reproducible Starter

This repository is a resumable research pipeline for evaluating whether Adaptive Hybrid GraphRAG improves repository-aware question answering over graph-only, vector-only, and fixed-hybrid baselines. It mines a repository knowledge graph, builds a Cypher-grounded benchmark with development/validation/hidden-test splits, runs eight comparable QA systems, and produces evaluation tables, statistical tests, ablations, and scalability measurements.

## Before anything else: credentials

Rotate your Gemini API key, Neo4j password, and GitHub personal access token before using this repository, and confirm `.env` is gitignored (it is, by default). **`.env.example` must only ever contain placeholder values** — it is a template meant to be shared/committed. If you ever find real secrets in `.env.example`, that means they were pasted into the wrong file; move them to `.env` and restore placeholders. Do not publish this repository until you've checked both files.

## Design rules

- **Gemini measures, Ollama phrases.** Gemini is used for every measured system output (the five/six/seven/eight systems' answers). Ollama is used only to phrase non-measured synthetic input text (synthetic commit messages/issue bodies) and optional benchmark question paraphrases — never for ground truth and never for a system's answer.
- **One shared generation config.** Every system's final-answer call uses the same temperature and token budget (`src/systems/prompts.py`'s `ANSWER_TEMPERATURE`/`ANSWER_MAX_OUTPUT_TOKENS`, both sourced from `config/experiment.yaml`) and the same `ANSWER` prompt text. The only intentional difference between systems is retrieval strategy — not prompt wording, temperature, or token budget.
- **Ground truth comes from executed Cypher, never from an LLM.** Every benchmark answer is produced by running a fixed, human-authored Cypher template against the live graph.
- **Tune only on dev/validation, never on hidden-test.** See Step 6.

## 1. Prerequisites

Install Python 3.11+, Git, Neo4j (AuraDB or local), and Ollama.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
ollama pull llama3.1:8b
```

Fill in `.env` with your own credentials (see the security note above). Then record your environment before doing anything else:

```bash
python -m scripts.record_environment
```

This writes `results/environment_manifest.json` and `environment-lock.txt` (OS, Python version, full `pip freeze`, Neo4j server version, Gemini/embedding model strings, and a source-code fingerprint if this directory isn't a git repo). Re-run it before every measured pilot or full run you intend to report.

## 2. Clone and mine the repositories

```bash
python -m src.ingestion.clone_repos
python -m src.ingestion.mine_repositories
python -m src.ingestion.repository_metadata
```

Raw JSONL is saved per repository in `data/raw/`. `repository_metadata.py` records the exact cloned commit SHA, snapshot date, branch, and entity counts to `data/metadata/<repo>.json` — this is what "record the repository commit SHA" (Step 11) points to. Reduce limits in `config/repos.yaml` for an initial test.

## 3. Preprocess and generate synthetic data

```bash
python -m src.preprocessing.preprocess_data --include-synthetic
python -m src.synthetic_gen.generate --commits 300 --issues 120 --prs 80
```

Relationships and IDs are generated first; Ollama only phrases text. For a fast smoke test without Ollama:

```bash
python -m src.synthetic_gen.generate --no-ollama --commits 30 --issues 12 --prs 8
```

## 4. Build and validate the Neo4j knowledge graph

```bash
python -m src.kg_construction.load_graph
python -m src.kg_construction.validate_graph
```

`validate_graph.py` checks orphan nodes/relationships, malformed dates, invalid developer identifiers, and incomplete pull requests, and cross-references `preprocessing_summary.json` so every missing relationship is labeled `excluded_by_preprocessing` (intentional filtering), `known_upstream_gap` (expected given your mining limits), or flagged as genuinely unclassified. Keep a copy of the printed node/relationship counts and `results/graph_validation_report.json` for the paper.

## 5. Build the local vector index

```bash
python -m src.build_vector_index
```

Embeds repository artifacts locally using SentenceTransformers and stores a FAISS index.

## 6. Generate the benchmark and freeze dev/validation/hidden-test splits

```bash
python -m src.benchmark_gen.generate_benchmark
python -m src.benchmark_gen.split_benchmark
```

The 300-question distribution is 40 structure, 40 code retrieval, 45 dependency, 35 documentation, 50 issue/PR, 30 developer activity, and 60 multi-hop questions, with the exact split accounting below. Ground truth is generated by executing fixed, human-authored Cypher templates — not by asking an LLM.

The frozen benchmark contains **300 questions in total**, partitioned into three mutually exclusive sets:

| Split | Questions | Purpose |
| --- | ---: | --- |
| Development | 29 | Development and tuning |
| Validation | 29 | Validation of tuning choices |
| Hidden test | 242 | Final evaluation after freezing the system |
| **Total** | **300** | **29 + 29 + 242 = 300** |

The other **58 questions are the 29 development and 29 validation questions**; none were discarded or omitted from the split. The question IDs in these three files are disjoint and together cover all 300 benchmark IDs. Counts are recorded in [`split_manifest.json`](data/benchmark/splits/split_manifest.json).

The hidden-test set contains 136 repository-holdout questions (`apache/airflow`), 48 additional template-holdout questions outside that repository, and 58 questions from the category-stratified remainder: **136 + 48 + 58 = 242**. After reserving the 184 holdout questions, the remaining 116 were split into 29 development, 29 validation, and 58 hidden-test questions. Thus, the 25% development and 25% validation fractions apply to the non-holdout remainder, not to all 300 questions.

**Unanswerable probes are separate from the 300-question benchmark and all three splits.** The generator targets approximately 20 additional probes for abstention-quality evaluation, accepting probes only after verifying zero matching graph results. The expected output, `data/benchmark/unanswerable_probes.jsonl`, is absent from this snapshot, so no realized probe count is established here. The approximately 20 probes must not be counted as part of the other 58 questions or reported as an evaluated set without the generated artifact and evaluation results.

`split_benchmark.py` produces `data/benchmark/splits/{dev,validation,hidden_test_answer_key,hidden_test_questions}.{jsonl,csv}` using repository holdout (one repository reserved entirely for hidden-test) plus template-novelty holdout (the rarest template per category reserved for hidden-test) plus category-stratified sampling for the rest. `hidden_test_questions.*` has every gold-revealing field stripped (including `answerable`, which would otherwise leak the abstention-quality label) — that is the only file a system should ever be run against for a number you intend to report as final. **Only `dev` and `validation` may be used to tune routing thresholds, fusion weights, or prompts** (Step 8). Do not open `hidden_test_answer_key.*` until the system is frozen.

Before the full experiment, manually inspect at least 10 questions from every category and compare them to Neo4j Browser and the source repository. Optionally check for training-data leakage (real risk here, since 4 of 5 source repositories are well-known OSS projects):

```bash
python -m src.benchmark_gen.leakage_check --benchmark-file data/benchmark/splits/hidden_test_answer_key.jsonl
```

## 7. Run the regression pilot

```powershell
powershell -File scripts/run_regression.ps1
```

Runs all eight systems against the frozen 7-question pilot and asserts each result against `data/benchmark/regression_expectations.json` (expected route where meaningful, non-abstention, expected answer entities, a latency ceiling, and that any logged Cypher is still read-only). Add every fixed failure to the expectations file so it never silently regresses. `plain_llm` and `vector_rag` are expected to fail most of these checks by design — that's the sanity check working, not a bug.

## 8. Tune on dev/validation, then run ablations

```powershell
powershell -File scripts/run_ablations.ps1
```

Runs the full system plus 12 ablation variants (no-vector, no-graph, no-routing, no-templates, no-fallback, no-validation, fixed 1/2/3-hop, and three fusion-weight configurations) against the dev split, reusing `adaptive_hybrid_graphrag.py`'s own codebase via `AblationConfig` rather than forked copies — every variant differs from the full system by exactly one mechanism. Use this stage to pick final routing confidence thresholds (`config/experiment.yaml` → `router`) and fusion weights on dev/validation only, then freeze them.

## 9. Run the full experiment

For the revised experiment using the same 242 questions and eight systems, see
[the adaptive routing protocol](docs/adaptive_routing_protocol.md). Prepare its
blinded inputs, source fingerprints, and resumable runner with
`python -m scripts.prepare_routing_evaluation`. This preparation makes no API
calls and preserves existing results. The protocol separates overall system
comparison from routing ablations and requires complete question/repeat coverage.

```bash
python -m src.systems.plain_llm --benchmark-file data/benchmark/splits/hidden_test_questions.csv
# ...repeat for vector_rag, langchain_graphrag, llamaindex_graphrag,
#    fixed_graph_rag, fixed_hybrid_rag, oracle_hybrid_rag, adaptive_hybrid_graphrag
python -m src.evaluation.metrics --input-dir results --benchmark-file data/benchmark/splits/hidden_test_answer_key.csv --bert-score
python -m src.evaluation.statistics --input results/per_question_metrics.csv
python -m src.evaluation.report_tables --per-question results/per_question_metrics.csv --ablations-dir results/ablations
```

`oracle_hybrid_rag` needs `--benchmark-file` to point at a file containing `expected_retrieval_route` (the answer key, since it reads the gold route — this is intentional; it is not a practical system, it estimates a routing ceiling). Every other system should be run against the gold-stripped `hidden_test_questions.*`. Add `--repeats 3` to any system if you need to measure variance under nondeterministic generation; each repeat is tagged with `run_id` and a composite `run_key` so resumption never confuses one repeat for another.

`statistics.py` reports Wilcoxon signed-rank tests, paired bootstrap 95% confidence intervals, rank-biserial effect sizes, and Holm-corrected p-values, broken out overall and per category/difficulty. `report_tables.py` writes the five thesis tables (main performance, category breakdown, reasoning-depth breakdown, ablation table, failure analysis) as CSV under `results/report_tables/`.

All system runners are resumable. On restart they keep successful rows and
automatically retry rows that previously recorded an API or network error; no
`--reset` is needed. Gemini RetryInfo delays and transient connection drops
are retried. A daily quota exhaustion still needs provider capacity before the
resumed run can complete.

## 10. Annotate hallucinations (blinded)

```bash
python -m src.evaluation.hallucination_annotation --results-dir results
```

Produces a blinded sheet (`results/hallucination_annotation.csv`, no system column, shuffled row order) and a private key file annotators should never see. Label each answer `supported`/`unsupported`/`contradicted`/`incomplete`/`irrelevant` and, where relevant, a `failure_source`. Use at least two independent annotators (save each copy under a distinct filename), then:

```bash
python -m src.evaluation.agreement --sheets results/annotator_a.csv results/annotator_b.csv
```

Reports Cohen's kappa (two annotators) and Krippendorff's alpha (any number, missing-value tolerant) per label column. Only join annotations back to the private key file after annotation is complete.

## 11. Scalability testing

```bash
python -m src.scalability.generate_and_measure --sizes 1000,5000,10000
```

Builds a realistic Repository/Developer/Commit/File subgraph (not label-only nodes) under a size-specific label prefix, runs 1-hop/2-hop/3-hop/aggregation graph queries and a separate local FAISS vector-index measurement, 5 repetitions after 1 warmup, reporting median and IQR. **Use a dedicated local Neo4j instance for the README's larger sizes (10000–500000)** — the default sizes here are intentionally small so this is safe to run once against a shared instance as a smoke test. Never point a large-scale run at your benchmark database.

Run date, exact Gemini model string, package lock (`environment-lock.txt`), Neo4j version/deployment, embedding model, repository commit SHA (`data/metadata/`), benchmark split manifest (`data/benchmark/splits/split_manifest.json`), generation parameters (`config/experiment.yaml`), RPM throttle and any retried/failed calls, hardware, graph counts (`results/graph_validation_report.json`), leakage-check results, and the annotation procedure plus inter-annotator agreement.

## The eight systems

| System | Retrieval | Notes |
|---|---|---|
| `plain_llm` | none | No repository access; measures what the model already "knows." |
| `vector_rag` | vector only | Semantic chunk search. |
| `langchain_graphrag` | graph only | LLM-generated Cypher every time, no templates. |
| `llamaindex_graphrag` | graph only | Same shape as above, framed as a property-graph query engine. |
| `fixed_graph_rag` | graph only | Registered templates only, no LLM-Cypher fallback — abstains if no template matches. |
| `fixed_hybrid_rag` | graph + vector, always both | No routing decision. |
| `oracle_hybrid_rag` | graph and/or vector, per gold route | Not a practical system — a routing-ceiling estimate. |
| `adaptive_hybrid_graphrag` | routed, with fallback | The system under study: confidence-based routing, a template→LLM-Cypher→vector fallback ladder, and evidence validation. |

## Research questions and hypotheses

**RQ1.** Does graph retrieval improve repository-question answering over a plain LLM and vector RAG?
**RQ2.** Does combining vector and graph retrieval improve performance over either alone?
**RQ3.** Does adaptive routing improve the quality–latency trade-off over a fixed hybrid strategy?
**RQ4.** Which question categories and reasoning depths benefit most from graph or hybrid retrieval?
**RQ5.** How robust is the framework across repositories, question formulations, and graph sizes?

**H1.** Graph-based systems achieve higher structural-question accuracy than Plain LLM and Vector RAG.
**H2.** Vector RAG is competitive or superior on semantic documentation questions.
**H3.** Fixed Hybrid RAG improves retrieval recall over vector-only and graph-only retrieval.
**H4.** Adaptive Hybrid GraphRAG achieves comparable or better answer quality than Fixed Hybrid RAG while reducing latency or LLM-call count, particularly under API rate-limit pressure (a fixed-hybrid or always-two-call system pays every question's full latency; a routed system with a fallback ladder pays it only when the first attempt fails).
**H5.** Adaptive traversal improves performance on multi-hop questions.
**H6.** Evidence validation (`retrieval_core.validate_evidence`) reduces unsupported claims and hallucinations.
**H7.** Performance degrades as graph size and reasoning depth increase, but Adaptive Hybrid degrades more slowly than the baselines.

Do not insert expected numeric values into result files or this README before the final run — report observed numbers only, from `results/report_tables/` and `results/statistical_tests.csv`.

## Research cautions

Do not change prompts between systems after seeing outcomes. Freeze the benchmark, splits, and code before the final hidden-test run — no further tuning once `hidden_test_answer_key.*` has been opened. A generated Cypher query is checked for read-only operations (`src/common.py`'s `safe_read_cypher`), but run the experiment with a Neo4j account that has read-only permission wherever possible. Framework and model APIs change; pin a tested environment (`environment-lock.txt`) and preserve it with the final repository. Never rotate through multiple free-tier API accounts to evade a provider's rate limit — if you legitimately hold more than one Gemini key (e.g. separate billed GCP projects), `config/experiment.yaml` → `llm_key_pool` can spread load across them; otherwise request a paid-tier quota increase.
